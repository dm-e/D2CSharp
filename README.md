# 1. Project Overview and Goals

D2CSharp is a project for translating Delphi source code to C#.

A major part of the project is the development of a free runtime library (RTL) that provides the Delphi-compatible runtime functionality required by the C# code generated by D2CSharp.

The repository therefore contains not only the tools required for translation, but in particular:

- an independently created MockRTL,
- the actual D2CSharp RTL,
- Delphi test programs,
- the C# files generated from those tests,
- manually reworked comparison versions,
- and Visual Studio projects used to verify the translations.

## 1.1 D2CSharp and Delphi2CSharp

D2CSharp uses the same basic translation technology as the commercial Delphi2CSharp product, but is intentionally much simpler.

D2CSharp does not provide freely configurable translation options. Paths and other settings required by the intended project workflow are predefined.

Compared with Delphi2CSharp, D2CSharp does not provide, among other things:

- configurable preprocessor conditions,
- refactoring functions,
- DFM translation,
- generation of a life-cycle manager,
- configurable generation of mock routines.

D2CSharp is therefore not a complete replacement for Delphi2CSharp.

Even in this deliberately reduced form, however, D2CSharp can already be highly useful for practical conversion tasks.

For projects that do not require complex preprocessor configuration, DFM translation, or additional refactoring functions, the converter can automate a substantial part of the work that would otherwise have to be done manually.

Even if additional work is still required afterwards, the automatic rule-based translation provides a consistent starting point and can significantly reduce the amount of manual porting work.

## 1.2 Rule-Based Translation

D2CSharp works according to predefined translation rules.

Given the same source code, the same configuration, and the same tool version, it therefore produces reproducible C# output.

This ensures that generated code follows a consistent translation strategy and can be compared and improved systematically over longer development periods.

The actual conversion is also fast and does not require repeated computation by a generative AI system.

AI tools may of course be used when contributing to the development of the project. Regardless of whether AI tools are used, all contributions must comply with the applicable licensing and copyright requirements.

In particular, proprietary original source code from the Delphi RTL or from other components that are not appropriately licensed must not be copied or incorporated into the free RTL without the necessary rights.

## 1.3 Project Scope

The current focus of the project is the Delphi Runtime Library and fundamental Delphi language constructs.

The existing tests currently use RTL units only. VCL units are not yet part of the test suite.

A large number of the existing test files cover functions and language constructs that were already available in Delphi 7. These files therefore use the prefix `d7_`.

D2CSharp and the associated free RTL are under active development.

Especially during the early stages of the project, new test cases are expected to require changes to the converter, additions to the MockRTL, or further implementations in the D2CSharp RTL.

The test structure is intended precisely to make such unsupported cases visible and reproducible.

As development progresses, the proportion of Delphi programs that can be translated correctly to C# without manual post-processing should continue to increase.

## 1.4 Current Development Status

The project is still at an early stage of development, but the current repository already provides a working basis for further development and testing.

The current test suite contains 66 Delphi test files. At present, 40 of them are translated without requiring manual corrections to the generated C# code.

Test cases that are not yet fully functional are temporarily disabled where necessary so that the complete test application can still be built and executed.

The current RTL implementation includes a comparatively complete `System.cs`.

`SysUtils.cs` is already present, but many of its routines are still stubs and therefore do not yet provide the required runtime behavior.

Several RTL units required by the existing tests have not yet been implemented. These currently include:

- `StrUtils`
- `Math`
- `Classes`
- `DateUtils`

Problems found in the current test set can have several different causes:

1. A required RTL unit has not yet been implemented.
2. A required routine in `SysUtils.cs` is still only a stub.
3. A required routine is missing from an RTL unit that already exists.
4. An existing RTL routine may be incomplete or incorrectly implemented.
5. The converter itself may still require changes.

The differences between `TestsGenerated` and `TestsWorking` show where the generated C# code currently requires manual post-processing.

Files that are identical in both directories require no manual changes. Files that differ indicate cases that still need investigation or correction.

At this stage, further changes to `D2CSharp.exe` are expected to be necessary as additional language constructs and RTL functionality are covered by the tests.

As the converter, the MockRTL, and the D2CSharp RTL are improved, the number of manually reworked test files should gradually decrease.

## 1.5 Documentation

A complete standalone user manual for D2CSharp is currently not part of this repository.

Its operation and basic concepts are similar in many respects to Delphi2CSharp. The Delphi2CSharp documentation can therefore be used as a reference:

- Online help: [Delphi2C#](https://www.texttransformer.com/d2csharphelp/index.html)
- PDF manual: [Delphi2CSharp.pdf](https://www.texttransformer.com/downloads/Delphi2CSharp.pdf)

The workflows specific to this repository, including the MockRTL, test translation, post-processing, and verification, are documented in this README and in `CONTRIBUTING.md`.

# 2. Requirements

## 2.1 C# and .NET

The supplied Visual Studio projects are SDK-style .NET projects and currently target `.NET 10` (`net10.0`).

A current version of Visual Studio with the .NET 10 SDK installed is recommended for development and verification of the C# sources.

## 2.2 Requirements for Delphi Sources

D2CSharp and Delphi2CSharp require syntactically and semantically valid Delphi code.

The Delphi source code to be translated should therefore compile successfully with the Delphi compiler before it is passed to D2CSharp.

Invalid or incomplete Delphi code may result in follow-up conversion errors whose messages do not necessarily indicate the actual underlying cause.

This applies in particular to the test sources in this project:

A test should first compile and run correctly on the Delphi side before its C# translation is evaluated.

## 2.3 Preprocessor Directives

Test files intended for D2CSharp should not contain Delphi preprocessor directives.

Unlike Delphi2CSharp, D2CSharp does not provide configurable settings for preprocessor conditions.

Source code that depends on conditional compilation can therefore result in conversion errors that are difficult to interpret.

This is also one of the technical reasons why the original Delphi RTL sources cannot simply be translated with D2CSharp and used as the basis for the D2CSharp RTL.

The Delphi RTL makes extensive use of conditional compilation and is not designed for this simplified conversion workflow.

Independently of this technical limitation, proprietary Delphi RTL source code is not used as the basis for the free D2CSharp RTL for legal reasons.

Instead, the project uses the independently created sources under `MockRTL/Source`.

## 2.4 Delphi Versions

The primary goal is to translate Delphi code for the current Delphi compiler.

Using the current Delphi compiler is not, however, a strict requirement for creating test cases.

Contributors who do not have access to the current compiler may also create tests with older Delphi versions.

Where possible, a Delphi version should be used in which the `string` type is already Unicode-based. This better matches the direction of the current D2CSharp RTL.

Some existing tests intentionally cover language and RTL features that were already available in Delphi 7.

This is indicated by the `d7_` prefix and does not mean that Delphi 7 is the preferred or primary target version of the project.

# 3. Setup and Getting Started

## 3.1 Setting Up the bin Directory

The executable tools `D2CSharp.exe` and `ExtractReworked.exe` are not stored in the Git history of the repository.

They are provided separately as release assets.

After downloading the release package, extract its contents into the repository's `bin` directory.

The resulting structure should include at least:

```text
bin/
  D2CSharp.exe
  ExtractReworked.exe
  README.txt
  Licenses/
```

The license files supplied with the programs must be kept together with the executables.

The licensing of these programs is separate from the licensing of the remaining repository files.

The files under `Projects` expect the executable programs at the predefined paths under `bin`.

D2CSharp currently does not provide freely configurable paths for these tools.

## 3.2 Getting Started as a Developer

After cloning the repository, the basic steps for a first test are:

1. Download the current D2CSharp release asset.
2. Extract the contents of the release package into the `bin` directory.
3. Verify that `D2CSharp.exe` and `ExtractReworked.exe` are present there.
4. Run `Projects/D2CSharp.bat`.
5. Compare the generated files under `TestsGenerated` with the versions under `TestsWorking`.
6. Apply corrections under `TestsWorking` if required.
7. Open the solution under `D2CSharpTests` in Visual Studio.
8. Build and verify the RTL and test projects.

After changes to tests, the MockRTL, or RTL files, the regeneration and comparison workflow is run again.

# 4. Repository Structure

## 4.1 Repository Root

The repository root contains the general documentation and license files for the project.

These include in particular:

```text
CONTRIBUTING.md
LICENSE
LICENSE-MPL-2.0.txt
NOTICE
README.md
```

The licensing of individual components is described in Section 9.

## 4.2 bin

The `bin` directory is intended for the executable tools required to work with the repository.

These include in particular:

- `D2CSharp.exe`
- `ExtractReworked.exe`
- the associated README
- the associated license files

The executable files themselves are distributed as release assets and are not stored in the Git history.

## 4.3 MockRTL

The `MockRTL` directory contains a simplified representation of the Delphi RTL structure required for conversion.

Within this project, the term `MockRTL` refers to declaration-oriented RTL skeletons and stub implementations. It does not refer to a unit-test mocking framework.

The directory mainly consists of `Source` and `Converted`.

### 4.3.1 MockRTL/Source

`MockRTL/Source` follows the structure and unit naming of the Delphi RTL.

The files are not copies of the Delphi RTL sources.

They were created independently from the Delphi original sources on the basis of publicly available information for the purposes of this project.

The files serve two separate purposes within D2CSharp.

First, they form the input from which the C# files under `MockRTL/Converted` are generated.

For this purpose, the Pascal files provide the required declarations and a skeleton structure suitable for conversion.

Second, they control the translation of the actual test and application code.

D2CSharp obtains information from them about, among other things:

- constants,
- classes,
- structures and other types,
- and the signatures of referenced routines.

The MockRTL therefore describes part of the environment in which the Delphi code being translated is to be interpreted.

It is not only the starting point for the later C# RTL implementation, but also an essential source of information used during translation.

The routines themselves normally contain no actual RTL implementation.

Procedures are empty, functions return appropriate default values, or they contain only the minimal structure required for translation.

As development progresses, these files may be extended and improved, for example when additional declarations, type definitions, constants, or routines are required for new test cases or additional RTL functionality.

The MockRTL is primarily maintained and provided by t2t-soft.

Suggestions, corrections, and contributions from other developers are explicitly welcome.

### 4.3.2 MockRTL/Converted

The files under `MockRTL/Converted` are generated automatically with Delphi2CSharp from the corresponding Pascal files under `MockRTL/Source`.

They represent the C# counterparts of the MockRTL.

Changes to the MockRTL should generally be made in the Pascal source files under `MockRTL/Source`.

The files under `MockRTL/Converted` are generated files and are regenerated afterwards.

## 4.4 D2CSharpRTL

The `D2CSharpRTL` directory contains the actual C# implementation of the runtime library required by D2CSharp.

Its directory structure and many of its file names correspond to the structure used under `MockRTL`.

While the routines in the MockRTL serve only as declarations or simplified stubs, the corresponding routines in `D2CSharpRTL` contain the actual implementations.

`D2CSharpRTL` therefore provides the functional runtime library used by the C# code generated by D2CSharp.

In addition to the RTL files derived from the MockRTL structure, the directory contains additional C# helper classes developed specifically for D2CSharp and provided by t2t-soft.

These helper classes extend the reconstructed RTL where additional functionality is required for a practical or technically appropriate implementation in C#.

The applicable license is determined by the license notice in the respective file.

Directly implemented helper classes may be subject to a different license than RTL files derived from the Mock sources.

## 4.5 Tests

The `Tests` directory contains the Delphi test programs used as the common starting point for verifying translation results.

The existing test files mainly cover fundamental language and RTL features that were already available in Delphi 7.

Many of these files therefore use the `d7_` prefix.

The current test suite is only the beginning of a much larger set of tests.

It will be extended with additional test cases as the project develops.

## 4.6 TestsGenerated

`TestsGenerated` contains the C# source files generated automatically by `D2CSharp.exe` from the Delphi files under `Tests`.

These files represent the direct and unchanged result of the conversion.

They are not corrected manually.

They may therefore still contain translation errors or C# code that does not compile successfully or does not behave as expected.

`TestsGenerated` thus documents the actual state of automatic translation produced by the version of D2CSharp currently in use.

## 4.7 TestsWorking

`TestsWorking` contains the working versions of the generated C# test files.

After regeneration, all files from `TestsGenerated` are initially copied to `TestsWorking`.

If an automatically generated file still contains errors, the required corrections are made in the corresponding file under `TestsWorking`.

`TestsWorking` is therefore intended to contain a functional C# version of the test programs.

The two directories deliberately serve different purposes:

- `TestsGenerated` contains the unchanged output of the converter.
- `TestsWorking` contains the functional version, including manual corrections where necessary.

## 4.8 TestsReworked

`TestsReworked` contains those files from `TestsWorking` that differ from their counterparts under `TestsGenerated`.

The directory therefore contains only tests for which manual post-processing is still required after automatic conversion.

`TestsReworked` is not maintained as a permanently independent parallel source tree.

As part of the development workflow, it is regenerated automatically from the differences between `TestsGenerated` and `TestsWorking`.

The number of files contained there therefore also indicates which existing tests still require improvements in the automatic translation.

## 4.9 Projects

The `Projects` directory contains files used to control conversion processes within the repository.

For distribution, `D2CSharp.bat` is currently the main file intended to be included.

Running this batch file starts the central regeneration and comparison workflow.

Additional project or batch files that may exist during development are not necessarily part of the public distribution.

## 4.10 D2CSharpTests

`D2CSharpTests` contains the Visual Studio and .NET projects used to verify the generated and manually reworked C# sources.

### 4.10.1 D2CSharpTests/D2CSharpRTL

`D2CSharpRTL/D2CSharpRTL.csproj` is the library project for the actual D2CSharp Runtime Library.

It contains the completed C# implementations of the required Delphi RTL functionality together with the additional C# helper classes.

### 4.10.2 D2CSharpTests/Tests

`Tests/Tests.csproj` is the test project.

It depends on `D2CSharpRTL.csproj` and includes the functional C# test files from `TestsWorking`.

The files are not copied into the project directory, but are included as linked files.

This keeps `TestsWorking` as the central storage location for the working test sources while allowing the same files to be compiled and tested directly in Visual Studio.

### 4.10.3 D2CSharpTests/Formatting

The `Formatting` directory contains two helper projects and the batch file `FormatAll.cmd`.

`GeneratedFormatting.csproj` includes the C# files from `TestsGenerated` as linked source files.

`WorkingFormatting.csproj` does the same for the files under `TestsWorking`.

These projects serve as workspaces for `dotnet format` and are not intended to be standalone libraries of the D2CSharp RTL.

`FormatAll.cmd` applies consistent whitespace formatting to both sets of files.

This makes `TestsGenerated` and `TestsWorking` much easier to compare with diff tools such as WinMerge.

Differences caused only by indentation or formatting are reduced, making the actual manual changes easier to identify.

# 5. Test File Structure and Conventions

No dedicated test framework is intentionally used for these tests.

This allows the same test sources to be used as directly as possible in Delphi and, after translation, in C# and optionally C++.

Dependencies on a language-specific test framework would make this goal more difficult.

Instead, the test files consist of simple test functions that each return a Boolean value.

A successful test returns `True`; a failed test returns `False`.

## 5.1 Common Test Function

Each test unit should additionally contain one common test function that calls all individual test functions in sequence and combines their results.

The basic pattern is:

```pascal
function TestUnitName: Boolean;
begin
  Result := True;
  Result := Result and TestFunction1;
  Result := Result and TestFunction2;
  Result := Result and TestFunction3;
end;
```

The common test function therefore returns `True` only if all associated individual tests succeed.

The `interface` section of a test unit should normally contain only the declaration of this common test function.

The individual test functions and any helper elements used only within the unit should be declared in the `implementation` section.

## 5.2 Naming Conventions

Names of classes, interfaces, functions, and other test-related identifiers should contain an abbreviation derived from the name of the corresponding test unit.

This reduces the likelihood of name collisions with identifiers from other test units.

The names of the common test functions have so far mostly been written in lowercase only.

This is not a technical requirement and is not intended to be a mandatory rule for future tests.

## 5.3 Character Set

Only ANSI characters should be used in the test sources.

This is intended to avoid unnecessary differences in the way the source files are handled by different compilers, converters, editors, and target languages.

## 5.4 Comparing Results

A test should be written so that the original Delphi code and the generated code in C# and optionally C++ produce the same result.

The aim is that the actual test logic does not require target-language-specific modification after translation.

If tolerances are required for particular calculations or data types, they should already be handled in the Delphi test.

The Delphi test file therefore defines the result considered acceptable for all target languages.

# 6. Development and Test Workflow

`Projects/D2CSharp.bat` automates the main workflow used to regenerate the tests while preserving existing manual corrections.

## 6.1 Detecting Existing Manual Changes

First, `ExtractReworked.exe` is executed.

The program deletes the existing files under `TestsReworked`.

It then compares the files under `TestsWorking` with their counterparts under `TestsGenerated`.

All files that differ are copied to `TestsReworked`.

This preserves exactly those versions that contain manual changes compared with the most recently generated output.

## 6.2 Regenerating the Tests

Next, `D2CSharp.exe` is executed.

The Delphi test files under `Tests` are translated again to C# and written to `TestsGenerated`.

`TestsGenerated` then contains the current unchanged output of the converter.

## 6.3 Copying the Generated Files to TestsWorking

All files from `TestsGenerated` are then copied to `TestsWorking`.

At this point, `TestsWorking` initially represents the current automatic translation in full.

## 6.4 Restoring Existing Manual Changes

The files previously saved under `TestsReworked` are then copied back to `TestsWorking`.

These files overwrite the newly generated versions.

Existing manual corrections are therefore preserved across a new translation run.

## 6.5 Formatting

Finally, `D2CSharpTests/Formatting/FormatAll.cmd` is executed.

The files under `TestsGenerated` and `TestsWorking` are formatted consistently.

Both versions can then be compared directly, for example with WinMerge.

## 6.6 Review After Regeneration

After running `D2CSharp.bat`, `TestsGenerated` and `TestsWorking` must be reviewed again.

Changes to `D2CSharp.exe` may cause previously necessary manual changes to be generated correctly automatically.

Because existing files from `TestsReworked` are copied back over the newly generated versions in `TestsWorking`, such converter improvements are not automatically incorporated into files that were already manually reworked.

The developer must therefore compare the corresponding files under `TestsGenerated` and `TestsWorking`.

Improvements in the generated code that are hidden by an older manually reworked version may need to be transferred manually into `TestsWorking`.

Likewise, newly introduced translation problems must be corrected there.

During the next run of `D2CSharp.bat`, `ExtractReworked.exe` will again determine automatically which files still require manual post-processing.

## 6.7 Goal of the Workflow

As `D2CSharp.exe`, the MockRTL, and the D2CSharp RTL are improved, the automatically generated C# code should increasingly approach the functional versions under `TestsWorking`.

With an unchanged set of tests, the number of files under `TestsReworked` should therefore decrease over time.

A file can disappear from `TestsReworked` once D2CSharp generates it correctly without manual post-processing.

An increase in the number of files under `TestsReworked` does not necessarily indicate a regression.

It may also result from the addition of new test cases whose complete support still requires improvements to D2CSharp or the RTL.

# 7. Interpreting Test Results

A failing test does not necessarily mean that the translation produced by D2CSharp is incorrect.

Especially during the early stages of development, some functions in the D2CSharp RTL may not yet be implemented or may only be partially implemented.

In such a case, the generated C# code may be syntactically correct while the test still fails to produce the expected result.

When a test fails, it should therefore be determined whether the cause lies in:

- the automatic translation,
- a missing or incomplete RTL implementation,
- the MockRTL,
- or the test case itself.

The tests therefore serve not only to verify the converter, but also to support the gradual completion and verification of the D2CSharp RTL.

Particularly during the early stages of the project, a substantial number of changes to the converter itself should be expected.

Changes to the converter are made by t2t-soft, because its source code is not part of this repository.

# 8. Contributions

Contributions to the project are welcome.

Contributions are particularly useful in the following areas:

- completing and improving the MockRTL,
- implementing missing RTL functionality,
- correcting existing D2CSharp RTL implementations,
- adding focused new test cases,
- and providing the functional C# implementations required by new tests.

New tests are welcome.

However, because very large numbers of test files can be created quickly and every additional test may require further work on the converter or RTL, new tests should be added in a focused manner.

Contributions are especially useful when a new test case is accompanied by a working C# version or by the RTL implementation required for that test.

The source code of `D2CSharp.exe` is not part of this repository.

Converter defects therefore cannot be submitted directly as changes to the converter itself.

In such cases, however, a small reproducible Delphi test case and a corrected C# version are particularly helpful.

Detailed contribution rules are provided in `CONTRIBUTING.md`.

# 10. Background

The original technical interest behind the tools used in this project was the development of parser generators.

Work on Delphi converters later grew out of specific customer projects.

These projects have so far mainly involved translating relatively simple Delphi code or transferring the basic structure of existing software to C# or C++.

D2CSharp now pursues a broader goal:

In addition to translating the Delphi source code itself, the runtime functionality required by that code is to be provided step by step in a freely available RTL.

The range of Delphi code that can be translated without manual post-processing should therefore continue to expand over time.
